# Business contact Worker — staged compatible hardening

**Status (2026-11-07): IMPLEMENTED IN STAGING, NOT LIVE.**

Files:
- `index.js`: the stage-1 candidate replacement for production `suncoast-lead-form`.
- `test.mjs`: Node.js 22 automated regression suite (20 scenarios).
- `.github/workflows/staged-contact-worker-tests.yml`: branch-only syntax/test CI; **no deployment step**.

The staged candidate was adapted from `feature/contact-email-otp/worker/legacy-lead/index.js` but **removes its OTP-gateway enforcement**. This is essential: production HTML forms currently POST directly to the Worker and the email OTP gateway has not been activated. Deploying the original OTP-dependent replacement would reject legitimate leads.

## Behavior preserved

- `POST` from existing website forms (urlencoded and multipart FormData).
- Existing Turnstile widget sends `cf-turnstile-response`; server verifies via Siteverify before delivery.
- Same 11 keys in Make.com JSON: `name`, `email`, `phone`, `help`, `source`, `page_name`, `utm_source`, `utm_campaign`, `utm_term`, `utm_medium`, `landing_page`.
- Missing optional fields are empty strings; `lead_source` defaults to `Suncoast B2B Landing Page`.
- Customer website reviews use the same endpoint and carry review rating / consent in the `help` message as generated by the existing page JavaScript; the Worker doesn't strip that message.
- Success response: `302 Location: https://business.suncoasttechsupport.net/thank-you.html`.
- Failure remains an HTML page with a link to the form and support phone.

## New protections

- Uses Cloudflare **encrypted Worker secrets**, not hardcoded credentials:
  - `TURNSTILE_SECRET`
  - `MAKE_WEBHOOK_URL`
- Requires Siteverify `success === true` and exact hostname `business.suncoasttechsupport.net`; fails closed on invalid/used token or verification outage. Does **not** require `action` because existing widgets do not set a custom action.
- Restricts Make webhook to HTTPS `hook.<region>.make.com`; current production webhook hostname `hook.us2.make.com` matches.
- Validates email/name, caps individual fields, rejects file submissions, and restricts HTTP body to 16 KB using both declared Content-Length and actual stream size.
- Removes logging of lead PII and webhook response body. Errors return informative but non-sensitive HTML; no output is treated as delivered if Make fails.
- Rejects unsupported methods and content types.

## Known limitations / not part of Phase 1

- No new request-level rate limiting or IP throttling yet. This comes with the endpoint hardening phase.
- Existing `workers.dev` remains reachable until a separate, validated protected route is activated.
- The residential `suncoast-b2c-lead-form` Worker remains unchanged.
- Production and residential Workers share the existing Turnstile secret. **Do not rotate/invalidate it without a coordinated B2B+B2C change.**
- The Make webhook URL currently embedded in production source should be rotated using a controlled, tested Make.com handoff. Do **not** invalidate the current webhook before confirming the new one works.
- Offline tests mock Cloudflare Siteverify and Make.com. **A green CI run does not establish that real leads reach Zoho.**
- Turnstile action validation, email reveal, email OTP and public email removal remain separate approval-gated phases.
- Normal page conversion attribution may use browser sessionStorage; do not alter the redirect or page script without retesting conversions.

## Test and deployment gates

1. **Baseline (read-only):** With approval, submit a controlled test lead through the current business and residential forms and confirm entry in Make.com, Zoho, email notification, and the thank-you page. Capture a known-good Worker source/version and rollback route.
2. **Stage clone:** Create a non-production Worker, set fresh test-only encrypted bindings, and test one known-safe Make scenario. Do not point live forms to the clone.
3. **Turnstile validation:** Prove that the deployed test token returns `hostname=business.suncoasttechsupport.net` with the site's current widget. Check that valid submissions work and invalid/expired/replayed tokens fail.
4. **Secret coordination:** Define separate rotation plan covering both B2B and B2C, and a new Make webhook + downstream Zoho mapping. Store secrets only in the Cloudflare dashboard/API secret bindings, not in GitHub, chat, test logs, or screenshots.
5. **Human review / explicit approval:** Review staging evidence and a rollback procedure before any production deployment. Do not update the existing live Worker automatically.
6. **Small production cutover only after approval:** Deploy business Worker change, verify a real submission and associated contact funnel, and monitor immediately. B2C is a separate cutover.
7. **Endpoint protection:** Only after the forms are reliable, plan protected same-origin routing, rate limits and retirement of unused `workers.dev` exposure. Avoid premature access restrictions.
